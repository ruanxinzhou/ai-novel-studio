# spec 3 · 一致性引擎（伏笔三态 + 角色知情边界）

- 日期：2026-10-22
- 状态：已落地（28 项新测试全通过；回归基线 39 failed / 394 passed 不变，passed 增至 422）
- 范围：`entities/store.py` 数据模型 + `entities/extractor.py` 回账 + `review/book_checks.py` 检查 + `context/ledger.py` 注入

## 背景

三方对照后确认的两个洞，都会导致长篇崩坏且当前无法被检查。

### 洞1：伏笔的「推进」是空注释

`store.py:520` 的 `ForeshadowSuggestion.kind` 声明了 `new | paid | advanced`，但 `apply_diff` 只处理 `new_foreshadows` 与 `foreshadow_payoffs` 两条路径，`advanced` 从不被读。

后果：`appearances` 只记「出现过」，分不清「被提到一句」和「真的往前推了一步」。而 `ledger.py:788` 的到期伏笔排序用的是 `min(e.appearances)`——一条被提到 10 次但从未推进的伏笔，账龄算出来是 0，永远排在最前，实际上已经死了。

### 洞 2：角色没有「不知情」

现有只有 `knowledge_of_supernatural`（对超自然的知情度，单值）与 `knows_about`（有向边，A 知道 B）。有向边能表达「谁知道」，但**无法表达「谁还不知道」**——那需要反查全图。

在无限流设定下这是核心崩坏源：唐迟从平行世界穿越来，他知道原剧本某些事，NPC 不知道。一旦模型让 NPC 说出不该知道的话，现有检查一个都拦不住。

## 一、伏笔推进落地

### 数据层

`Foreshadow` 加两个字段：

| 字段 | 类型 | 语义 |
|---|---|---|
| `last_advanced_ch` | int | 最近一次「推进」的章号，`0` = 从未推进 |
| `advance_count` | int | 累计推进次数 |

配套 `FORESHADOW_OPS = ("plant", "advance", "pay", "drop")` 枚举，与现有 `ENTITY_STATUSES` 并列。

### 关键设计：推进不改变 status

伏笔状态机仍是 `planted → paid / dropped`。**推进是正交的一维，不是第三个状态。**

skill 那边把埋/推进/回收当三态，那是简化。本项目不跟：「推进了 3 次但还没回收」的伏笔应显示为「已埋（推进 3 次）」，而不是一个新状态——这样账龄与回收状态能各自独立演进。

### 操作路径

两条生产路径共用一个写入方法 `EntityStore.note_foreshadow_advance(eid, chapter)`：

1. **AI 抽取确认**：`apply_diff` 新增第三个分支 `foreshadow_advances`（旧代码在
   `StateDiff` 里声明了这个桶但从不读，勾选也不生效）；
2. **定稿回账**：`reconcile_foreshadows` 问出 `advanced` 名单后调用同一方法。

```python
def note_foreshadow_advance(self, eid: str, chapter: int | None) -> Entity:
    e = self.get(eid)
    if e.type != "foreshadow":
        return e
    ch = chapter or 0
    if ch and ch == e.last_advanced_ch and e.advance_count > 0:
        return e                      # 同章幂等：重跑定稿不刷爆计数
    e.last_advanced_ch = ch
    e.advance_count += 1
    e.updated_at = _now()
    self._flush()
    return e
```

**幂等是必须的**：定稿回账可以重跑，不做同章去重的话 `advance_count`
会被刷成虚高，「推进 N 次」这个信号就废了。

**删章/插章联动**：`shift_chapter_refs` 的 dry-run 与赋值两处都同步偏移
`last_advanced_ch`（它也是章号引用），否则删章后账龄凭空多一章。

## 二、账龄排序修正

到期伏笔排序从 `min(appearances)` 改为 `last_advanced_ch`，没推进过的排最前。

理由：真正该被催的是「很久没推进」的，不是「很久没出现」的。一条每章都被提到但从没推进的伏笔，正是最该被处理的——按旧排序它永远显示「刚埋」，永远排在最后。

文案区分两种状态（「账龄」改称「静默」，因为它算的是距上次推进而非距埋设）：

```
- 鞋柜第二层的信封（第3章埋，已静默 8 章，从未推进，本章必须处理）
- 猫眼里的倒影（第5章埋，已静默 6 章，上次推进在第6章（累计 2 次））
```

同一口径也用在**实体账本**（`state:entities`，续写大纲时注入）：
`（第1章埋，从未推进）` / `（第1章埋，第1章推进过）`。

## 三、角色知情边界

### 数据层

给 `character` 加两个可追踪属性（进 `ENTITY_ATTRS` 白名单，与现有 8 个并列）：

| key | label | 语义 |
|---|---|---|
| `knows` | 已知信息 | 明确知道的 |
| `blinded_to` | 不知情 | 明确不知道的 |

**为什么不放进 Voiceprint**：voiceprint 是恒定的创作设定（口癖、习惯动作），知情边界**随剧情变**——第 3 章他不知道，第 7 章他知道了。这是 `state_attrs` 的语义。放错地方会导致「角色卡上写着他不知道，但他早就知道了」这种无法追踪的矛盾。

### 检查层

新增 `check_knowledge_boundary`（第八条书规），接入 `book_review_checks`。

判定逻辑**极其保守**——四个条件同时成立才报：

```
1. 本章是成稿（正文 ≥ 600 字，半成品一律放过）
2. 实体 X 显式声明了 blinded_to，且切出的关键词 K 出现在正文中
3. X 的名字附近（≤20 字）出现认知动词：竟然/居然/知道/看穿/早就/心里有数…
4. 同一句里没有困惑类反向信号：不知道/一头雾水/莫名其妙/皱眉…
```

条件 3 是关键：**知识边界是「谁」的边界**。同一个秘密在场上有别的角色知道
完全合法，只有「被声明不知情的那个人表现出知道」才叫越界。

**不做反向推断**（不检查「他应该知道却不知道」），那需要世界模型，成本与误判率都不可控。

**关键词长度限 [2, 12]**：单字（「命」「局」）在正文里撞车率极高，超长句
根本不是可校验的信息点。

**为什么软提醒而非 P0**：启发式匹配，误判率天然高。按 `check_foreshadow_payoff`
的先例，只在成稿且命中明确时报，不阻断交稿。

**空值 = 不检查**：不自动填 `blinded_to`，由 brief/embody 阶段 LLM 产出、作者可编辑。没填就不报。

## 四、任务书注入

知情边界进第四段（本章人物与设定）角色行尾：

```
- 老陈：看门人（第1-3章）（已知：唐迟是第七个住客；不知情：猫眼里的东西）
```

**为什么注入而不只做审稿检查**：审稿是**事后**报警，写这一章时模型
根本不知道这条边界；注入才是让模型在写的时候就守住边界。没声明的角色
不加这段——不自动推断「他应该知道什么」，凭空推断会把正确信息也判成越界。

## 六、实施中发现的三个坑

1. **`paid`/`advanced` 加错了函数**：`apply_diff` 与 `merge_extracted` 都以
   `return {...}` 结尾，改动误落到后者，导致 `NameError` 打挂 4 个既有测试。
   教训：dataclass 状态文件里两个函数返回结构相似，编辑前必须确认行号归属。
2. **文案改动会撞既有测试**：「已欠 N 章」→「已静默 N 章，从未推进」不是
   纯措辞，它是新语义的一部分，旧断言必须同步改而不是当成回归失败放过。
3. **`reconcile_foreshadows` 才是生产主路径**：`apply_diff` 是 AI 提议确认通道，
   实际写作流程里定稿回账问出的 `advanced` 才是常态。只改 `apply_diff`
   等于改了一条没人走的路。

## 七、明确不做

- **不做「应该知道」的推断。** 只查明确声明的「不知情」被越过。
- **不做伏笔状态机的三态重构。** 推进是正交维度，不是第三个状态。
- **不改 `appearances` 的语义。** 它仍是「出现过」，只是排序不再依赖它。
- **不自动填 `blinded_to`。** 空值 = 不检查。
- **不做资源 delta 账本。** 那是账本轴的第五个字段，与一致性引擎无关，另议。
